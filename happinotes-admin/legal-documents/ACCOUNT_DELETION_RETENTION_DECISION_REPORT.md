# HappiNotes — Account Deletion Retention Decision Report

**Prepared:** 2026-11-04
**Company:** AIRASKILL CITY PRIVATE LIMITED
**Purpose:** Give the owner and legal/finance reviewers a source-based inventory for deciding what the account-deletion worker should erase, anonymize, retain, or defer. This is a technical audit, not a legal opinion. It does not state a retention period or legal basis.

## Executive audit finding

The backend does not currently complete account deletion. It sets the account to `pending`, deletes authentication artifacts and matching OTPs, clears collections/favourites/push-token references, replaces the profile name with a generic tombstone label, resets role/language, unsets email/phone, clears `purchasedBooks`, and unsets the embedded subscription entitlement. It retains the User `_id` and deletion fields, `StorePurchase`, `SubscriptionPurchase`, and `AccountDeletionRequest`; it does not process external support, provider, runtime log or backup data. The worker pauses at `blocked_policy` with purchase, provider, support, log, backup and audit disposition unresolved. It does not mark the overall request complete. No worker path marks the user or request completed.

The gate is intentional. Ordinary profile/contact fields and HappiNotes entitlements are removed before the gate. The internal account key remains pseudonymous linkage while purchase/subscription records remain. The gate does not mean those records have an established legal retention basis; it prevents completion until finance/counsel decide the field-level disposition and any necessary evidence is separated and protected.

**Decision consequence:** These statutes identify possible accounting-record duties, but do not let engineering conclude that `StorePurchase`, `SubscriptionPurchase`, `User.purchasedBooks`, embedded `User.subscription`, or the whole `User` document must be retained. No row is released from the existing `blocked_policy` gate on this research alone. Finance/counsel must name each retained field, applicable provision, trigger, access restriction, and disposal condition; records outside that defined exception need an approved deletion/anonymisation disposition.

## Cross-cutting consequences and controls

- **Store cancellation is separate.** The deletion worker does not call Google Play or Apple to cancel renewal. A user must cancel in the store. Removing the HappiNotes User or entitlement alone would not stop store billing.
- **Purchase restoration depends on ownership evidence.** Store verification and notification routes use local purchase/subscription claims, store transaction keys, product IDs, and account-linked identifiers. Do not remove ledgers before deciding how future restore, refund/revocation, and ownership checks will work.
- **The User record is the linking point.** Purchase ledgers reference `User._id`; request history also references it. Deleting the User document does not automatically cascade-delete those rows in the inspected code.
- **No application support-ticket store or backup cleanup path was found.** Those areas require owner/provider inventory, not assumptions based on the app models.
- **No retention durations or legal grounds are supplied in this report.** The legal/finance reviewers must decide them based on the company’s actual obligations and provider contracts.
