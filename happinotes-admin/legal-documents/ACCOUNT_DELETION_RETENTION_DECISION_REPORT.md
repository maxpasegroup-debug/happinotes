# HappiNotes — Account Deletion Retention Decision Report

**Prepared:** 2026-11-04
**Company:** AIRASKILL CITY PRIVATE LIMITED
**Purpose:** Give the owner and legal/finance reviewers a source-based inventory for deciding what the account-deletion worker should erase, anonymize, retain, or defer. This is a technical audit, not a legal opinion. It does not state a retention period or legal basis.

## Executive audit finding

The backend does not currently complete account deletion. It sets the account to `pending`, which blocks ordinary account access, removes password-reset tokens and OTP rows associated with the account’s email/phone, clears `bookCollection`, `favourites`, and `fcmTokens`, and then stops at the retention-policy gate. It does not delete the `User` document, `purchasedBooks`, embedded subscription entitlement, `StorePurchase`, `SubscriptionPurchase`, or `AccountDeletionRequest` records. At the gate, the worker marks `personalDataCleanup` and `entitlementPolicy` as `deferred_policy`; it does not mark the overall request complete. No path in the inspected worker marks the user or request `completed`.

The gate is intentional. The worker code says the account identity, store purchases, subscription purchase ledger, subscription entitlement, and financial/audit handling remain policy-dependent. The report therefore lists choices for owner/legal/finance review without recommending a period or pretending a law applies.

## Owner direction received

The current task brief supplies a high-level intended disposition, recorded in [FINAL_ACCOUNT_DELETION_OWNER_DECISION.md](FINAL_ACCOUNT_DELETION_OWNER_DECISION.md): anonymise profile personal fields; erase email/phone except approved retention; delete authentication secrets; delete favourites, collections and push tokens; retain only necessary transaction evidence with restricted access; remove Premium only after purchase/subscription handling; minimise support data; apply approved log/backup expiry; and keep minimal restricted deletion history. This is operational direction only, not legal/finance approval. The actual permitted fields, legal grounds, retention periods, backup/vendor requirements and completion conditions remain undecided. The specifically referenced prior owner-decision file was not found in the repository; the linked record was created from the instructions in the current task.

## Cross-cutting consequences and controls

- **Store cancellation is separate.** The deletion worker does not call Google Play or Apple to cancel renewal. A user must cancel in the store. Removing the HappiNotes User or entitlement alone would not stop store billing.
- **Purchase restoration depends on ownership evidence.** Store verification and notification routes use local purchase/subscription claims, store transaction keys, product IDs, and account-linked identifiers. Do not remove ledgers before deciding how future restore, refund/revocation, and ownership checks will work.
- **The User record is the linking point.** Purchase ledgers reference `User._id`; request history also references it. Deleting the User document does not automatically cascade-delete those rows in the inspected code.
- **No application support-ticket store or backup cleanup path was found.** Those areas require owner/provider inventory, not assumptions based on the app models.
- **No retention durations or legal grounds are supplied in this report.** The legal/finance reviewers must decide them based on the company’s actual obligations and provider contracts.

## Owner decision checklist

For every row above, the owner and reviewers should record:

1. The disposition: erase, anonymize, retain with restricted access, or defer.
2. The approved reason and applicable legal/finance reviewer (do not infer these from the code).
3. The approved retention period or event-based criterion, where applicable.
4. Which stores, backups, archives, logs, mailboxes, and vendors are in scope.
5. The technical owner and acceptance evidence for implementing the decision.
6. Which successful backend checkpoints must be true before the system can set `AccountDeletionRequest.status = completed` and `User.deletionState = completed`.

Until those decisions and implementation exist, the current retention-policy gate should remain in place. Do not set a request to completed manually or remove purchase/transaction records as part of this decision exercise.
