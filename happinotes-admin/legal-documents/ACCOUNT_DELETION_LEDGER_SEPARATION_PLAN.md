# HappiNotes — Account Deletion Ledger Separation Plan

**Company:** AIRASKILL CITY PRIVATE LIMITED  
**Status:** Engineering plan only. No code, schema, database, or production changes were made.  
**Basis:** `ACCOUNT_DELETION_FINANCIAL_DATA_DECISION.md` and read-only inspection of the purchase, subscription, notification, restore, and account-deletion source paths.  
**Decision boundary:** This plan does not establish that any field must be legally retained or set a retention period. The existing `blocked_policy` gate remains in force until owner, finance, and counsel approve field-level dispositions and a separate implementation/release stage is authorized.

## 1. Current design and constraints

`StorePurchase` and `SubscriptionPurchase` are already in collections separate from `User`, but each ledger has a required `userId` reference to `User._id`. Those records currently act as both transaction claims and the lookup needed for account ownership and store notification processing.

The one-time purchase ledger also stores `bookId`, `productId`, `active`, and timestamps. The subscription ledger stores `planKey`, `productId`, `priceVersion`, `active`, `expiresAt`, `autoRenewing`, `providerStateSignedAt`, and timestamps. Neither schema contains the actual amount paid, tax/GST amount, invoice, refund amount, or refund date. The existing unique index on `{ store, transactionKey }` provides duplicate-claim protection within each ledger collection.

The User document separately stores `purchasedBooks` and an embedded `subscription` object. The deletion worker clears `purchasedBooks` and unsets `subscription`, then stops at `blocked_policy`; it does not unlink the purchase ledgers. Store notifications can refresh ledger state, while the entitlement update functions refuse to grant access to a non-writable account.

Notification ownership checks currently depend on `userId`: Google compares its obfuscated account identifier to a deterministic token derived from the User ID; Apple verifies `appAccountToken` against that same account token. Restore verification also queries claims by `userId` and rejects a claim owned by another account. Therefore, simply making `userId` optional without updating these paths would break provider reconciliation and could create unsafe restore behavior.

## 2. Recommended target

Use the existing transaction-ledger collections as the provider-transaction and duplicate-claim record, but make an account association optional after deletion. Do not copy or retain a full `User` profile to preserve a purchase. Do not add a durable identity map by default.

While a user account is active, the ledgers may keep `userId` and the fields required by current verification and entitlement flows. When deletion reaches the approved financial-evidence stage:

1. The worker first confirms the ordinary profile/authentication cleanup and that `User.purchasedBooks` and embedded `User.subscription` are cleared.
2. For each purchase/subscription row linked to that User, preserve only the field allowlist approved by finance/counsel; unset `userId` and any other unapproved fields. A missing `userId` means permanently detached from an app account.
3. Keep the unique transaction key and store discriminator only if their provider-verification, refund/revocation, or duplicate-prevention purpose is approved. These identifiers may remain pseudonymous/linkable even without a `User` reference.
4. Store notifications may update a detached row's provider state, but the detached row has no path back to a User entitlement. Restore endpoints must reject detached claims and must never reattach them to a new account.
5. The financial-evidence collection remains inaccessible to ordinary customer APIs. Any staff access is separately authorized, narrowly scoped, and recorded.

This is a design recommendation, not approval to retain the proposed fields. If finance/counsel determine that a transaction key or product field is unnecessary, it must not be kept merely to preserve a convenient restore flow.

## 4. Notification, restoration, and duplicate-claim rules

### Google Play

- Continue authenticating Pub/Sub push identity and using the Android Publisher API to fetch authoritative state.
- Resolve the verified transaction key and product to an existing `StorePurchase` or `SubscriptionPurchase` record. Never create a claim from an RTDN alone.
- For a linked active account, retain current account-token verification. For a detached record, update only the evidence row after provider signature/identity, product, package, and transaction-key checks pass; do not call an entitlement writer.
- A restore request is account-authorized and must match an existing claim's non-null `userId`. If the claim is detached, return a non-restorable/deleted-account result and do not attach the claim to the current account.

### Apple

- Continue verifying signed notification and transaction data, application/environment, product, and original transaction chain.
- For a linked active account, retain current `appAccountToken` comparison. For a detached record, provider-verified transaction key/product/chain may update evidence only. If an approved account-binding check is needed, decide it before implementation and assess whether the retained token is still personal/linkable data.
- Restore must reject a detached claim even when the Apple transaction itself is valid. Valid provider purchase is not by itself authorization to restore access to a deleted HappiNotes account.

### Shared duplicate protection

- Keep a unique provider-transaction key while any approved evidence/claim remains. Unlinking `userId` must not delete the row or unique key unless the approved disposal process explicitly requires it and duplicate-claim risk has an approved replacement.
- Preserve separate transaction type semantics: a one-time product claim and a subscription claim have different lifecycle operations. If the ledgers are ever unified, use a unique compound key including store, transaction kind, and canonical provider transaction key; preflight cross-collection collisions first.
- Never use a deleted user's `User._id`, email, or phone to reassign a detached transaction. No account-transfer mechanism is included in this plan.

## 5. Proposed financial evidence access controls

- No customer-facing endpoint returns evidence rows, raw provider tokens, internal account IDs, or staff audit data.
- Keep ordinary admin user/listing APIs limited to fields needed for their documented function; do not add transaction evidence to `getUsers` or general deletion-request responses.
- Define a finance-specific permission and named roles before adding any evidence query/export. Require authentication, least privilege, purpose-limited filters, pagination, and field minimization.
- Audit every read/export and any status correction with staff actor, timestamp, action, and internal transaction-row reference. Do not put raw transaction tokens, full transaction keys, email, or phone in application logs.
- Consider collection-level database roles or a dedicated service credential if the deployed database supports them; this requires production architecture review and is not assumed by this source-only plan.
- Review access regularly under an owner-approved process. No retention duration or review interval is specified here.

## 6. Migration and rollout sequence (future authorization required)

1. Obtain the owner/finance/counsel field allowlist and disposition approval. Keep the policy gate unchanged while decisions are pending.
2. Inventory model consumers, existing index definitions, collection validators, duplicate transaction keys, orphan `userId` references, and legacy key formats on a sanitized non-production copy. Do not emit transaction values in logs or reports.
3. Implement backward-compatible readers/writers that accept linked rows and detached rows. Ensure all entitlement writes require an active linked account; ensure every restore path rejects detached rows.
4. Add only the approved deletion-time unlink/minimization checkpoint. It must be idempotent, lease-fenced, fail closed on collision/unknown key format, and verify absence of links before completion.
5. Rehearse interruption/retry and notification/restore cases using provider test/sandbox data in a separately authorized verification stage. No tests were run as part of this plan request.
6. Review authorization and audit logging for retained evidence; verify data minimization and all public wording against the actual behavior.
7. Obtain separate approval before production schema/data migration or deployment. Do not treat this plan as permission to run either.

## 7. Acceptance conditions for a later implementation review

- Approved field-level evidence allowlist and documented owner/finance/counsel decisions exist without invented legal grounds or periods.
- Deleted accounts have no `User.purchasedBooks` or embedded `User.subscription` access state.
- Their retained ledger rows no longer contain a direct `userId` reference after the approved separation checkpoint; only specifically approved fields remain.
- Google and Apple notifications can update transaction evidence without writing to any deleted account's entitlements.
- Restore cannot claim, transfer, or reattach a detached transaction to another account.
- Unique transaction protection remains effective for linked and detached records, including verified legacy key formats.
- Staff access is least-privilege and auditable; standard APIs and logs do not expose financial evidence or raw tokens.
- Partial failures remain retryable/idempotent, lease-fenced checkpoints reflect verified row state, and the request remains `blocked_policy` until all other required deletion obligations are satisfied.
- No endpoint, admin action, or rollback path can manually mark deletion completed.

It also does not establish a lawful retention period, an identity-binding exception, or production MongoDB transaction/index/validator capabilities.
